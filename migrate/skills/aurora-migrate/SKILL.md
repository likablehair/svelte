# Migrating an app to @likable-hair/svelte v5

v5 is a rewrite: components, props, callbacks, icons, tokens and CSS changed. The rules are known to the migration tool, so you do not need to know the whole library: follow the phases, and read a component's specs only when a remaining point needs it.

Tools: the `aurora` MCP server (`migration_analyze`, `migration_setup`, `migration_codemod`, `migration_next`, `migration_status`, `migration_rules`, plus `get_component`, `get_example`, `validate_usage`). Without MCP, the same phases are commands: `npx @likable-hair/svelte-migrate analyze|setup|codemod|next|status <app-dir>`, or `node <library repository>/migrate/src/cli.ts analyze|setup|codemod|next|status <app-dir>` from a clone of the library repository while the package is not published. The other tools are commands too, run in the app folder: `svelte-migrate rules <Name>` (`migration_rules`), `svelte-mcp component <Name>` (`get_component`), `svelte-mcp example <Name> [id]` (`get_example`), `svelte-mcp validate <file...>` (`validate_usage`); from a clone, `node <library repository>/mcp/src/cli.ts component|example|validate …`. Use them instead of reading the library sources or MIGRATION.md.

## Ground rules

- **Never commit.** The tool and you only change files; the user reviews and commits.
- Start right away, on the current branch and with whatever is in the repository: branches, commits and stashes are the user's business. Do not ask for a clean repository or create a branch.
- Migrate the **whole app**, then test everything: v4 and v5 do not coexist.
- Ask the user before changing behaviour that the rules do not decide.

## Phases

1. **Analyze** (`migration_analyze`, read-only). Read the summary with the user: phase 0, automatic changes, things to check, manual points by file, wrappers, app-level steps.
   - **Phase 0**: if the app is on Svelte 4 or library v3, first run `npx sv migrate svelte-5` and fix the v3 syntax it reports, then analyze again.
2. **Setup** (`migration_setup`): the v4 code as it is (recorded in the git folder for `next`, uncommitted changes included), the svelte-check errors the v4 code already has (recorded in the git folder, before the install), v5 and `@mdi/js` in package.json, layer order and fonts in the main CSS, `v4-compat.css` when the app uses v4 color tokens, `setDefaultLocale` for non-English apps (with paraglide 2, `setDefaultLocale(() => getLocale())`, and `<html lang="%…%">` placeholders are left alone), `setTitleTemplate` with the name of the app `<title>` (PageHeader writes the tab title), coding agents configured. `migration_setup` does not install: **ask the user to run the install** (from the root of the workspace when the app is in one). The CLI `setup` installs, unless `--no-install`. `codemod`, `next` and `status` stop until v5 is installed, because svelte-check and the types would still be v4. After the install, **restart the dev server with `vite dev --force`** (or delete `node_modules/.vite`) if it was running: Vite keeps serving the v4 package it had pre-bundled.
3. **Codemod** (`migration_codemod`, `dryRun` first if the user wants to see it): renames, `{ detail }` removed, MDI names to `@mdi/js`, v4 defaults kept only where behaviour would change. It also **dissolves the `Standard*` wrappers and the `LabelAnd*` components** (a label next to a field: v5 fields have `label`): every use becomes the library component, keeping what the wrapper props meant (`style` → `variant`, `error` → `state`, `href`, `hint`, `title`) and the layout measures (widths, margins); the wrapper's look (colors, padding, heights, radii, shadows, extra elements) is dropped, and wrapper files nobody imports any more are deleted. Wrappers of a native `<select>`/`<textarea>` become `Select`/`Textarea` (options renamed `text` → `label` where they are built, in the same file); a click guard on `disabled`/`loading` is dropped, since the v5 `Button` ignores those clicks. It can be run again.
   - Show the user the **Wrappers** section of the report: per wrapper, the uses dissolved, the file deleted or kept, and "Look dropped with the wrappers", which they can put back as CSS variables if they want.
4. **Remaining points**, file by file, with `migration_next` (CLI: `next`): it runs svelte-check and returns the next file to fix, each error with the rule that explains it, and the points **to write** in that file (code the tool could not change). Fix the file, call it again; `migration_status` gives the whole list. Errors that were already in the v4 code (recorded by setup) are listed apart: they are not part of the migration, leave them unless the user asks. The order is components before the pages that use them: an error on an app component tag (`via`) is often fixed once, inside that component.
   - when an explanation is not enough, `migration_rules <Name>` shows the whole rule and `get_component` the v5 API;
   - **wrappers the codemod kept**: the Wrappers section says why ("why kept": Svelte 4 syntax, code of its own, no library component) and "Not done" lists the uses it skipped (`wrappers/<Name>`: a prop with logic, a value it could not map, options built in another file: rename their keys as the reason says, then run the codemod again). Dissolve them by hand with the same rule (keep the meaning and the layout, drop the look, tell the user what you dropped); keep a wrapper only if it has real logic, and say so;
   - **app components that passed props through a dissolved wrapper** (for example `LabelAndTextfield` spreading `{...rest}` into the old `StandardTextfield`): the report notes "the spread may carry …", and svelte-check flags those props where the component is used. Add them to the component and map them as the wrapper did (`error` → `state={error ? 'error' : undefined}`);
   - run `validate_usage` on every file you change.
5. **To write, then to look at**: when no errors are left, `migration_next` lists first the points **to write**, file by file: do them. They are read from the v4 code: a point leaves as soon as its use no longer has what triggered it (the v4 prop, event or snippet), has the prop that settles it (an accessible name, `currentPath`) or is gone; the points the tool cannot verify stay listed after you do them, so go through them once. The migration is over when no errors are left and every point to write has been done once. Then the points **to look at, by component** (behaviour, look or a default changed: most need no code), each with the pages that use it, and the **pages to try**. Show that part to the user: they try the pages; the tool cannot verify look and behaviour. Write code for a point to look at only where the page relied on the old behaviour.
   - **If the app runs** (its dev server is up, or you can start it) and you have a browser tool, open each page to try in light and in dark mode (`<html data-mode="light">` / `"dark"`), take a screenshot of each and look at them before handing over: boxes that blend into the page, missing borders, text stuck to what follows, controls that lost their look. Fix what comes from the migration and show the screenshots to the user with what you changed.
   - On the same pages, **read the browser console**: v5 renders the desktop layout on the server, so invalid HTML that v4 never rendered there (a `<div>` inside an `<svg>` or a `<p>`, a `<button>` inside a `<button>`) now breaks the hydration ("hydration_mismatch", "node_invalid_placement"). Fix the markup.
   - Also try the pages **at phone width** (about 375px) and check that the page does not scroll sideways: the v4 scroll box of the layout clipped wide content, the window does not. Flex and grid children that hold tables or long text need `min-width: 0` (`min-w-0`).

## What the app looks like afterwards

The Aurora theme with the prototype fonts (Geist, Bricolage Grotesque, Geist Mono); v4 color overrides of the app keep working through `v4-compat.css`. Texts follow `setDefaultLocale`. `setup` adds `@likable-hair/svelte-migrate` and `@likable-hair/svelte-mcp` to the dev dependencies: while the first is there, the app counts as being migrated (migration tools and this skill stay available after v5 is installed). When the migration is over, remove `@likable-hair/svelte-migrate` and run `npx svelte-mcp init`: it removes this skill and keeps `aurora-design` for the everyday work.
