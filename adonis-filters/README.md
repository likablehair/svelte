# @likable-hair/adonis-filters

Applies the filters of `@likable-hair/svelte` (the JSON of `FilterBuilder`, sent by `Filters`, `DataTable` and `filtersToBuilder`) to Lucid queries of AdonisJS 5, 6 and 7. It replaces the `FilterModifierApplier` class copied into every backend.

```ts
import FilterModifierApplier, { type Modifier } from '@likable-hair/adonis-filters'

const query = User.query().where('tenantId', tenantId)
new FilterModifierApplier().applyModifiers(query, data.filtersBuilder)
```

`applyModifiers(query, modifiers, options?)` is also exported as a function. It accepts `filtersBuilder.toJson()` (`{ modifiers }`), its `modifiers`, or the string of `toQueryParam()`, and returns the same query with its own type.

## What it does

- **All the conditions go inside one `where` group**, so an `or` sent by the client never escapes the conditions the backend put on the query first (tenant, owner): `where tenant_id = 1 and (a = 1 or b = 2)`.
- **Every kind of condition** of the contract: `simple`, `object`, `grouped`, `in`, `inBuilder` (subqueries), `null`, `column`, `jsonSuperset` (also negated), `raw`; joins, `select`, `from`, `orderBy`.
- **Checks the JSON**: malformed filters, unknown operators and raw conditions throw `FilterError`, which AdonisJS answers with **400**. The only raw conditions accepted are the JSON casts made by the filters (`(??#>>?)::numeric > ?`), with columns as identifier bindings.
- **Query-string parsing**: arrays longer than 20 items that `qs` turned into objects become lists again. Sending the filters with `toQueryParam()` avoids the other limits of `qs` (depth 5, numbers and booleans turned into strings).
- **`like`/`ilike` values are used as they are**: the v5 filters send the pattern (`%text%`, with `%` and `_` escaped).

## Options

| Option | |
|---|---|
| `columns` | Columns the filters may use (conditions, sorting, selected fields, join clauses), as the frontend writes them: `['name', 'users.email']` or a function. Without it every column is accepted. |
| `tables` | Tables the filters may read with `from`, joins and subqueries. Without it every table is accepted. |
| `legacyLike` | Wraps `like`/`ilike` values in `%` as the copied classes did. Only for frontends still on `@likable-hair/svelte` v4. |

Options given to the constructor apply to every call; those of a call win.

## From the copied class

1. Install the package and change the import: `#services/filter_modifier_applier` (or `App/Services/FilterModifierApplier`) becomes `@likable-hair/adonis-filters`. The types (`Modifier`, `WhereModifier`, `JoinModifier`, `WhereFilterValue`) have the same names.
2. Delete the copied file.
3. Apps whose frontend is still on v4: `new FilterModifierApplier({ legacyLike: true })`.
4. Check the results: an `or` at the first level now stays an `or` inside the group (some copies turned it into `and`), negated object and JSON conditions are negated, and the raw conditions written by hand on the frontend are refused.
5. Write `columns` and `tables` for each manager: the filters can otherwise read any column and table, also of other tenants through joins and subqueries.

## Development

The JSON types (`src/types.ts`) must stay equal to those of `src/lib/utils/filters/builder.ts` of the library: `tests/types.ts` fails to compile when they differ. The package imports nothing from AdonisJS: the query is a structural type (`FilterableQuery`) that the builders of Lucid 18, 21 and 22 satisfy. It ships ESM and CommonJS (AdonisJS 5 apps are CommonJS) with declarations readable by TypeScript 4.6.

From the root of the library repository:

```sh
npm install --prefix adonis-filters                   # Lucid 22 and AdonisJS 7, only for the tests
npx vitest run --project node adonis-filters/tests    # SQL generated by Lucid 22, no database needed
npx tsc -p adonis-filters                             # types and the contract with FilterBuilder
npm run build --prefix adonis-filters                 # dist/esm and dist/cjs
```
