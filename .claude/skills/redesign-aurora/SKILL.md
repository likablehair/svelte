# Redesign Aurora

Questo file è la memoria condivisa del progetto: lo leggono tutte le sessioni e tutto il team.

## Regola di manutenzione (prima di tutto)

- Quando l'utente prende, cambia o annulla una decisione, aggiorna questo file **nello stesso turno**, con la data.
- Una voce passa da "Proposte" a "Decisioni" **solo** quando l'utente la conferma esplicitamente.
- Se una decisione ne sostituisce un'altra, riscrivi la voce: niente informazioni contraddittorie una accanto all'altra.
- Quando un componente o un pezzo di infrastruttura è finito, aggiorna "Stato".
- Dopo ogni aggiornamento, dillo all'utente in una riga: "Skill aggiornata: ...".
- **Niente spazzatura dalla v4**: quando un comportamento della v4 non ha senso o è sbagliato (API gonfiate, accessibilità rotta, layout strani, id fissi…), va **segnalato all'utente** con una proposta migliore, non portato in silenzio. Elenco in "Comportamenti v4 scartati o da rivedere".
- **Gli usi interni non misurano il bisogno** (2026-10-08): la libreria la usano le app, fuori da questo repo, quindi 0 usi dentro la v4 non vuol dire che una prop, uno snippet o una variabile non serva. Si giudica **nel merito**: se ha senso si porta (o ha un equivalente); se è rumore, inutile o fatta male (es. il `range` di SimpleTextField) si toglie, segnalandolo all'utente. Gli usi interni sono solo un indizio di come si usa.

Se l'utente ha indicato un componente o un argomento (`$ARGUMENTS`), parti dalla sezione che lo riguarda.

## Ripartenza dopo un `/clear`

1. Leggi "Stato" (in fondo): l'ultima voce "Prossimo" dice da dove riprendere.
2. Il dev server delle docs gira su http://localhost:5180; se non risponde: `cd aurora && npx vite dev --port 5180` in background.
3. Segui "Processo per un componente". Per leggere componenti v4 grandi usa un subagente, così il contesto principale resta piccolo.
4. Quando un componente è finito e la skill è aggiornata, e l'utente dice "procedi", suggerisci `/clear` prima di iniziare il successivo (non puoi lanciarlo tu).
5. Leggi "Team, account e modo di lavorare" qui sotto: vale per chiunque usi la skill.

## Contesto

- Il repo contiene **due progetti separati**:
  - **root**: libreria attuale v4.3.2 (`src/lib`). È il **riferimento per il comportamento** dei componenti; si toccano solo i fix di manutenzione.
  - **`aurora/`**: la nuova libreria, riscritta da zero. Ha il suo `package.json` e il suo `node_modules`.
- In `aurora/` c'è il template library di SvelteKit 3:
  - la config sta in `aurora/vite.config.ts` (non esiste `svelte.config.js`);
  - nome `@likable-hair/svelte`, versione `5.0.0`, `"private": true`;
  - 0 dipendenze runtime, `"sideEffects": ["**/*.css"]`.
- Comandi, **da dentro `aurora/`**: `npm run dev`, `npm run check`, `npm run package`.
- Riferimenti:
  - `design/components-prototype.html`: il target visivo ("Likable Aurora UI"). Ogni card ha il percorso del componente v4 in `<div class="path">simple/buttons/Button.svelte</div>`, quindi un grep sul percorso porta alla sezione giusta.
  - `design/AUDIT.md`: bug e debolezze della v4 da non ripetere.
  - `design/REDESIGN-STRATEGY.md`: proposta sui token (sezioni 2–4) e livelli L0–L3. Le sezioni su fasi e rilascio sono superate.
  - Componenti v4: `src/lib/components/{simple,composed,layouts}/`. Pagine docs v4: `src/routes/docs/components/`. Gli array `props`, `styleProps` e gli snippet sono scritti a mano, ma servono come inventario dell'API.
- Per il confronto visivo con il prototipo c'è Playwright MCP, configurato in `.mcp.json` della root.

## Requisiti (dai brief delle tre task, svolte in parallelo)

1. **Componenti**
   - Avvicinare il più possibile l'aspetto di default al prototipo, prendendolo come ispirazione.
   - Ogni componente deve essere personalizzabile tramite variabili CSS.
   - Nuove tonalità di default, sia light sia dark, vicine al prototipo.
   - Il brief originale chiede di **non cambiare la logica** dei componenti e di chiedere prima se serve farlo. Vale anche nella riscrittura: il comportamento della v4 è la specifica, e ogni scostamento si chiede. Il "solo CSS" chiesto all'inizio dal capo è superato: il 2026-10-09 il capo ha approvato di cambiare anche la logica e le API quando serve, documentate in `aurora/MIGRATION.md`, purché la migrazione sia supportata da strumenti (punto 4).
2. **Documentazione**
   - Redesign ispirato al prototipo, possibilmente costruito con i componenti stessi della libreria.
   - Una pagina dedicata per ogni componente, con: esempio grafico, props, variabili CSS disponibili, snippet disponibili.
   - Le informazioni di ogni pagina devono essere comprensibili per un LLM che le legge dal web.
3. **Temi (plugin)**
   - Plugin che cambiano l'aspetto di default dei componenti **e di tutta l'app**.
   - Switchabili anche a runtime.
   - Cambiano **solo il design**, mai il comportamento o il layout dei componenti.
4. **Migrazione e rilascio** (chiesti dal capo il 2026-10-09, parte del restyling)
   - Un server **MCP** che effettua la migrazione delle app.
   - Un **prompt** per passare da una versione della libreria a un'altra.
   - **Test automatici** con Vitest o Playwright.
   - **Pipeline di rilascio** migliorata: bump della versione, GitHub release, pnpm, changelog.
   - **Da subito, per ogni componente** (deciso il 2026-10-09): i **test** e le **regole di migrazione** si scrivono insieme al componente, perché recuperarli dopo componente per componente costa di più. MCP, prompt e pipeline arrivano dopo e leggono le regole già scritte.

## Performance (misure del 2026-10-08)

Metodo: pagina temporanea con N righe di componenti in v4 e in v5 (stessi componenti), Playwright con CDP `Performance.getMetrics` (`RecalcStyleDuration`) in Chromium e tempo nella pagina (cambio + `offsetHeight`) in Firefox. 200 righe = 1400 istanze, ~3900 elementi. Le pagine di prova sono state cancellate; lo script era nello scratchpad.

- **Causa principale: le transizioni**, non le variabili. Al cambio di modalità ogni componente con `transition` sui colori avvia le sue transizioni: Button v5 120 ms contro 4 ms della v4 (1400 bottoni), tutto il mix 65 contro 22 ms in Chromium, 106 contro 43 in Firefox. Senza transizioni: Button 12 ms, mix 19 ms. Con la pausa delle transizioni (ex P28, `setMode`): Button 24 ms, mix 37 ms in Chromium; Button 13 ms, mix 67 ms in Firefox. Il doppio ricalcolo (attributo messo e tolto) costa circa il doppio del caso senza transizioni: accettato.
- **Token complessi (`color-mix()`, `light-dark()`)**: nessun costo misurabile. Sostituirli con colori fissi lascia i tempi uguali.
- **Registrare i token con `@property` (`<color>`)**: nessun guadagno, e con le transizioni peggiora (151 ms contro 120: i colori registrati diventano interpolabili). Non farlo.
- **Numero di custom property su `:root`** (oggi ~540, ~2000 a libreria completa): +2000 variabili finte costano +10–20% sul cambio modalità. Fonti esterne concordi: GitLab (+1,8% sul rendering) e web.dev (le proprietà ereditate costano al cambio, non per numero).
- Resta un costo per istanza 1,5–3× la v4 (ricalcolo completo: Button 9,5 contro 5,4 ms per 1400, Chip 22 contro 5,5), cioè pochi µs per componente: trascurabile per pagine reali.
- Regole per i nuovi componenti: transizioni solo sulle proprietà che cambiano con l'interazione; niente selettori universali con `::before`/`::after` nelle regole sempre attive; niente `@property` sui token.

## Lezioni dalla v4 (dettagli in `design/AUDIT.md`)

- Gli attributi nativi (`disabled`, `name`, `required`, `id`) devono arrivare all'elemento nativo. Nella v4 Button perdeva `disabled`.
- Mai `outline: 0` senza un sostituto `:focus-visible`.
- Niente import interni dal barrel (`$lib`, `#lib`): creano cicli. Usare percorsi diretti.
- Niente singleton globali né scritture su `document.documentElement` da dentro i componenti.
- Gli id si generano con `$props.id()`: niente id fissi o casuali (rompono l'SSR e si duplicano).
- Ogni `$effect` che aggiunge listener restituisce il cleanup. Se il valore si può derivare, usare `$derived`.
- Tutti i tipi pubblici vanno esportati da `src/lib/index.ts`.
- `{#each}` sempre con chiave.
- Nei componenti niente colori o px hardcoded: si usano solo token.
- Lo stile per istanza deve funzionare anche sugli overlay.

## Processo per un componente

1. **Specifica del comportamento**: leggi il componente v4 e la sua pagina docs. Elenca props, `$bindable`, snippet, callback e variabili CSS.
2. **Riferimento visivo**: trova la card del prototipo cercando il percorso del componente; guarda gli stati, le varianti, il light e il dark.
3. **Differenze e parità**: elenca ogni capacità della v4 e come si ottiene nel nuovo componente (gli usi interni alla v4 sono solo un indizio di come si usa, non di quanto serve: le app la usano fuori dal repo); quello che manca o si scarta va chiesto all'utente. Segnala i comportamenti senza senso. Ogni cosa che cambia comportamento o API va chiesta prima di implementarla. Le varianti visive in più (es. Button `secondary`, `danger`) sono da segnalare.
3b. **Contratto di personalizzazione**: verifica i 5 punti (variabili CSS per parte e stato, `class`, snippet per ogni contenuto, attributi nativi, stato in `data-*`).
4. **Implementazione** in `aurora/src/lib/components/...`, usando solo token.
5. **Variabili CSS**: per ogni parte visibile esponi background, colore, bordo, radius, padding, font, ombra, altezza, più gli stati hover, focus, active, disabled ed eventualmente error.
6. **Docs**: secondo le decisioni in vigore in quel momento (vedi P5).
7. **Verifica**: `npm run check` dentro `aurora/`; confronto visivo con il prototipo in light e dark e con almeno due temi; tastiera e focus.
7b. **Test** (obbligatori, ex P43): `aurora/tests/components/<Componente>.test.ts` con attributi nativi, prop → DOM e ARIA, eventi e `bind:`, tastiera, `data-*` e una prova per ogni bug v4 scartato; i suoi esempi docs entrano da soli nel test visivo. `npm run test` verde in Chromium e Firefox. Quello che hai verificato a mano nel passo 7 diventa un test.
8. **Export** da `aurora/src/lib/index.ts`.
8b. **Migrazione per umani**: aggiorna `aurora/MIGRATION.md` con tutto quello che rompe chi arriva dalla v4 (prop, tipi, default, callback, snippet, variabili CSS per istanza e `-default-*`, comportamento) e, in una riga, le aggiunte opzionali.
8c. **Migrazione per macchine** (obbligatoria, ex P44): `aurora/migrations/v4-to-v5/<Componente>.ts` con le stesse informazioni di 8b in forma di dati; le cose di giudizio vanno in `manual` con una spiegazione che un agente possa seguire.
9. **Aggiorna questa skill**: "Stato" ed eventuali decisioni.

## Convenzioni dei componenti (in uso)

- Ogni componente importa `../../../css/tokens.css` e il suo `Component.css`, che dichiara i `--{comp}-default-*` in `@layer global.base` su `:root`.
- **Layer e classi**: ogni file CSS e ogni `<style>` di componente inizia con `@layer reset, theme, base, global.base, global.theme, global.components, components, utilities;`. Nel `<style>` tutte le regole stanno in `@layer global.components { … }`, i `@keyframes` fuori. Le classi sono `aurora-{comp}` sulla radice e `aurora-{comp}-{parte}` sulle parti (`aurora-chip-close`, `aurora-text-field-hint`); i modificatori usano gli attributi `data-*` della radice (`.aurora-chip[data-variant='primary']`, `.aurora-button[data-size='sm']`), oppure classi prefissate se lo stato non è esposto (`aurora-button-icon-only`). Mai classi generiche. Lo script usato per convertire i primi 9 componenti avvolgeva lo `<style>` e rinominava i selettori; i nuovi componenti si scrivono già così.
- Nomi dei default: `--{comp}-default[-{size}][-{variant}][-{forma}][-{stato}]-{proprietà}` (es. `--button-default-danger-text-hover-background`). Le variabili per istanza non hanno variante né taglia (`--button-hover-background`) e valgono per tutte.
- Nel `<style>` del componente, varianti e taglie scrivono variabili private `--_*` sull'elemento; le regole leggono `var(--{comp}-x, var(--_x))` una volta sola. I selettori di forma o stato che devono vincere sulle varianti (es. `[data-shape='text']`, `[data-selected]`) vanno **dopo** nel sorgente (stessa specificità).
- Le prop di stato che le app collegano con `bind:` (es. `open`) si dichiarano `$bindable()` **senza default**: con un default, `bind:open={undefined}` (cioè `let open = $state()`) manda in errore la pagina (`props_invalid_value`).
- **Overlay modali** (Dialog, Drawer): `{#if open}` con `<dialog>` a tutto schermo che fa da contenitore; il backdrop è un `<div data-backdrop>` figlio (non `::backdrop`), così sfondo e pannello si animano separatamente e lo stile per istanza arriva. L'attachment `modal()` di `modal.ts` apre con `showModal()`, gestisce Esc (`keydown` con `preventDefault`, così Chrome non chiude da solo al secondo Esc), `cancel`, clic sul backdrop (pointerdown **e** click sul backdrop), submit di `method="dialog"`, `close` nativo, e restituisce il focus nel cleanup. Le animazioni sono **keyframes CSS** che leggono le variabili (durata ed easing presi direttamente dal CSS); in chiusura `out:leave` mette `inert` e `data-closing` sul `<dialog>` e aspetta `--_duration`. Blocco dello scroll: `:global(html):has(.dialog:modal) { overflow: hidden }` nel `<style>`.
- **Elemento esposto e usato internamente** (es. `menuElement`, `input`): tenerlo in uno `$state` locale e copiarlo nella prop, `bind:this={() => menuNode, (node) => (menuNode = menuElement = node)}`, e usare `menuNode` nel componente. Una prop `$bindable` che l'app non lega torna `undefined` quando il genitore rilegge le prop (uno spread che cambia, un `rerender`).
- **Hover e focus dei campi**: il selettore di hover esclude il focus (`.aurora-x-control:hover:not(:focus-within)`), altrimenti, essendo più specifico, vince sul bordo di focus mentre il puntatore è sul campo.
- **`aria-describedby` e `aria-invalid` passati dall'app** si uniscono a quelli del componente (`[rest['aria-describedby'], hintId].filter(Boolean).join(' ')`), mai sovrascritti: gli attributi scritti dopo `{...rest}` vincono sullo spread.
- **Variabili di stato che devono vincere sulla base** (es. `--chip-selected-*` su `--chip-background`): la proprietà legge una privata `--_bg-now` definita sulla radice come `var(--chip-background, var(--_bg))` e ridefinita nello stato come `var(--chip-selected-background, var(--chip-background, var(--_bg)))`; l'hover legge `var(--chip-hover-background, var(--_bg-now))`.
- Hover dentro `@media (hover: hover)` e sempre `:not(:disabled)`; focus con `outline` dai token `--global-focus-ring-*`; animazioni decorative spente con `prefers-reduced-motion`.
- **Commenti**: l'utente toglie i commenti esplicativi. Si scrivono solo quelli che hanno un effetto: `<!-- @component -->`, il JSDoc delle props nei `.svelte` e il JSDoc delle funzioni pubbliche esportate (es. `theme.ts`), che chi usa la libreria vede nell'editor. Niente commenti di spiegazione nel codice, nei CSS, nei temi.
- **Lingua**: tutto ciò che sta in `aurora/` (codice, JSDoc, `@component`, esempi, testi delle docs) è in inglese.
- **Docs (P5)**, tutto nel sorgente:
  - commento `<!-- @component Descrizione -->` in testa al componente (la prima frase finisce in `llms.txt`);
  - JSDoc su **ogni** membro dell'interfaccia `Props`, che va chiamata `Props`; default e `$bindable` nel destructuring di `$props()`;
  - nei `Props` i tipi si scrivono per esteso (unioni di stringhe), non con alias locali (`type Variant`, `Placement`): le docs mostrano il testo del tipo e l'alias nasconderebbe i valori;
  - i commenti nei file CSS sono solo note per chi legge, non hanno effetto sulle docs. Un token con un prefisso nuovo va aggiunto a `TOKEN_GROUPS` in `src/docs/api.server.ts`, altrimenti finisce nel gruppo "Altro";
  - esempi in `src/docs/examples/<slug>/NN-name.svelte` (nomi in inglese), con `<!-- @component Titolo\nDescrizione -->` in testa e import da `'#lib'` (nel codice mostrato diventa `'@likable-hair/svelte'`). Ogni esempio è codice copiabile: il layout dell'esempio sta nel suo `<style>`, non nelle classi delle docs.
  - Un componente che ne avvolge un altro dichiara `interface Props extends Omit<ComponentProps<typeof Base<Data>>, '…'>` e ridichiara solo le prop che cambiano: le docs mostrano le ereditate in "From Base". I metodi pubblici sono `export function` con JSDoc.
  - Un componente compare nelle docs quando è esportato da `src/lib/index.ts` con `export { default as X } from './components/...'`.

## Trappole note

- Node e TypeScript risolvono anche `../node_modules` della v4. Un import non dichiarato in `aurora/package.json` può funzionare per sbaglio, quindi le dipendenze vanno sempre dichiarate in `aurora/`.
- I comandi npm lanciati dalla root agiscono sulla v4, non su `aurora/`.
- L'ESLint della root ignora `aurora/**`.
- `sed -i` sostituisce il file con un rename e il watcher di Vite a volte non lo vede: il dev server continua a servire la versione vecchia (successo con Icon). Dopo modifiche fatte con `sed -i`, fare `touch` dei file o usare Edit/Python.
- Tailwind 4 mette `@layer properties;` in testa al CSS compilato, prima della riga dell'app: innocuo (contiene solo i fallback delle `@property`).
- Un file di tema dell'app deve dichiarare la riga completa (`global.base, global.theme, …`), non la forma corta `global`: se si carica prima della libreria, `@layer global.theme {}` creerebbe `global.theme` prima di `global.base` e i default vincerebbero sul tema.
- Il preset per Tailwind 3 è ESM: con `require()` da un config CommonJS arriva `{ default }`, quindi nelle docs si usa `import` (tutte le app hanno `tailwind.config.js` con `export default`).
- Aurora non ha Prettier: `npx prettier` lanciato su file di `aurora/` usa la config della root (2 spazi, 80 colonne) e rompe lo stile (tab, 100 colonne). Non lanciarlo.
- In SvelteKit 3 `$app/environment` è deprecato (si chiama `$app/env`) e svelte-check non ne trova i tipi: per sapere se si è in sviluppo usiamo `import.meta.env.DEV`. `$app/state` funziona.
- In questa macchina `rm` è un alias di `rm -iv`: con `-r` chiede conferma e blocca il comando. Usare `command rm`.
- SvelteKit 3 non ha l'alias `$lib`: si usano i subpath imports `#lib/...` dichiarati in `aurora/package.json` (solo nelle docs e nei test; dentro `src/lib` percorsi relativi).
- `light-dark()` accetta solo colori, non gradienti: per un gradiente diverso tra light e dark si mette `light-dark()` dentro ogni stop.
- `light-dark()` accetta solo colori (vale anche per le percentuali): per percentuali diverse tra light e dark va avvolto l'intero `color-mix()` (`light-dark(color-mix(... 10%), color-mix(... 14%))`).
- I token derivati e la scala del radius si calcolano su `<html>`: un override di `--global-color-primary` o `--global-radius-scale` su un sottoalbero non aggiorna i derivati, che vanno sovrascritti anche loro.
- Il focus ring è un `outline` (`--global-focus-ring-width`, `-color`, `-offset`), non un `box-shadow`: resta visibile in `forced-colors` e non si combina con le ombre della variante.
- Le ombre nei temi non valgono mai `none`: si usa `0 0 #0000`. I componenti le compongono in liste (`var(--global-shadow-fill), 0 6px ...`) e un `none` in lista invalida l'intera proprietà.
- Quello che un tema deve poter spegnere (gradienti, bagliori) va in token globali (`--global-fill-primary`, `--global-fill-error`, `--global-color-*-glow`), non nei default del componente.
- `pkill -f "<stringa>"` uccide anche la shell che lo lancia, se la stringa compare nel comando: fermare i server in background con l'ID del task.
- Un tema può indicare un font, ma non caricarlo: se l'app non carica quel font si vede il ripiego (nei temi demo: IBM Plex, Nunito, Fraunces, Didot non sono caricati).
- I temi usano `:root[data-theme='nome']`: funzionano solo su `<html>`, non su un sottoalbero.
- `$props.id()` va assegnato da solo (`const id = $props.id();`): dentro un template literal è un errore di compilazione.
- Il cleanup di un attachment (e di ogni effetto) dentro un `{#if}` con `out:` gira **dopo** l'outro e dopo la rimozione dal DOM: è il punto giusto per restituire il focus quando si chiude un `<dialog>` modale (prima la pagina è ancora inerte e `focus()` fallisce). Durante l'outro gli attributi del template non si aggiornano più (il ramo è in pausa): lo stato di chiusura va scritto sul nodo a mano (`leave` in `modal.ts`).
- Le durate delle chiusure si leggono da una variabile CSS (`--_duration`), non da `getAnimations()`: un'animazione infinita nel contenuto (lo spinner di un Button) darebbe durata infinita.
- Chi gestisce Esc dentro un overlay deve chiamare `preventDefault()`, altrimenti il `<dialog>` che lo contiene riceve anche la richiesta di chiusura nativa (`cancel`).
- Una prop chiamata `state` va rinominata nel destructuring (`state: validation`) se il componente usa la rune `$state`: altrimenti Svelte la legge come store (`store_rune_conflict`). La docs legge comunque il nome della prop.
- Menu e Drawer di un componente sono **fratelli** della sua radice, non figli: le variabili private `--_*` dichiarate sulla radice non li raggiungono, vanno dichiarate sulla parte che le usa. Per cambiare un default di un sotto-componente si imposta il suo `--{sub}-default-*` su una classe del sotto-componente (es. `--menu-default-max-height` su `.aurora-autocomplete-menu`), così il `--{sub}-*` per istanza passato dall'app vince ancora.
- Il Menu con `matchActivatorWidth` scrive la larghezza inline: `--menu-width` non ha effetto, per allargare o stringere si usano `--menu-min-width` / `--menu-max-width`.
- Playwright MCP salva gli screenshot solo dentro il repo (`.playwright-mcp/`, ignorato da git).
- Se il browser di Playwright MCP è occupato da un'altra sessione ("Browser is already in use"), si usa uno script con il pacchetto `playwright` della root (`node_modules/playwright/index.mjs`): Chromium con `executablePath` di `~/.cache/ms-playwright/chromium_headless_shell-1243/...` (la 1.59 della root cerca una build non installata), Firefox con `firefox.launch()` (installato). Su Firefox `waitUntil: 'networkidle'` non arriva mai (websocket di Vite): usare `load` + attesa.
- Il browser di Playwright MCP usa un profilo per cartella (`~/.cache/ms-playwright-mcp/mcp-chrome-*`): due sessioni Claude sullo stesso repo se lo contendono. Per trovare chi lo tiene: `command ps -e -o pid=,ppid=,args=` (anche `ps` è un alias, con le opzioni dà "conflicting format options"), il Chrome con quel `--user-data-dir` ha come genitore il `playwright-mcp` dell'altra sessione; la propria sessione si trova risalendo i `ppid` da `$$`. Terminare l'altra sessione solo se l'utente lo chiede (il 2026-10-08 l'ha chiesto). Con la sessione muoiono anche i suoi task in background, spesso il dev server su 5180: dopo, riavviarlo (`cd aurora && npx vite dev --port 5180` in background).
- Vite inlinea come data URI gli asset sotto 4 KB referenziati dal CSS: con `flag-icons` sono ~200 bandiere per formato, ~320 KB nel CSS dell'app (come nella v4). Rimedio documentato in FlagIcon: `build.assetsInlineLimit: (file) => (file.includes('/flag-icons/') ? false : undefined)`. Non verificato in una build reale.
- Cliccare su un campo subito dopo `navigate`, prima dell'hydration, mette il focus senza aprire il menu (manca `onfocus`): nei test aspettare ~1 s dopo il caricamento.
- Per misurare il costo degli stili in Chromium: `context.newCDPSession(page)`, `Performance.enable`, poi la differenza di `RecalcStyleDuration` di `Performance.getMetrics` prima e dopo l'azione. Il layout delle docs (sidebar, `docs.css`, 15 temi caricati) sporca le misure: toglierlo nella pagina prima di misurare.
- Anche `mv` è un alias interattivo (`mv -i`): usare `command mv -f`, altrimenti il comando resta fermo sulla conferma.
- `<selectedcontent>` copia l'opzione scelta solo quando cambia la selezione. Svelte la ricopia quando cambia il contenuto dell'opzione, ma il suo observer guarda `target.parentElement.closest('option')`: i cambi dei **figli diretti** di `<option>` non li vede. Il contenuto dinamico va avvolto in uno span (`display: contents`). Non mettere `<button><selectedcontent>` dentro un `{#if}` che si attiva dopo il mount: l'observer parte dopo la modifica.
- Lo stile di Chrome per `::picker(select)` ha `position-try-order: most-block-size` (si apre dove c'è più spazio, spesso sopra): con `normal` si apre sotto e gira solo se manca spazio.
- Un elemento fratello sovrapposto a un Button (la X del Dropdown) non eredita il colore del bottone: va ripetuta la catena `var(--button-color, var(--button-default-{variant}-color))`. Mai misurare i colori in JS: il tema cambia a runtime.
- Gli stati che un antenato nativo può imporre (`<fieldset disabled>` disabilita gli input) vanno stilizzati dalla pseudo-classe (`:disabled`, `:has(input:disabled)`), non dall'attributo `data-*` che riflette la prop: la prop non sa del fieldset.
- `<legend>` non è un elemento flex di un `<fieldset display:flex>` (è la "rendered legend"); con `float: inline-start` smette di esserlo e prende il `gap` come gli altri figli (verificato in Chromium e Firefox).
- Una variabile custom si risolve sull'elemento dove è dichiarata: `--_min-height: calc(var(--_rows) * 1lh)` sulla radice vuole `--_rows` sulla radice, non sul figlio (le unità come `1lh` invece si risolvono dove la variabile si usa).
- Nel markup di un `.svelte` con `lang="ts"` si può usare `as` di TypeScript: `{...rest as HTMLAnchorAttributes}` serve quando si spargono le prop di un `<button>` su un `<a>` (i tipi degli eventi non coincidono).
- Un `<dialog>` aperto con `showModal()` rende inerte tutto ciò che non sta nel suo sottoalbero, **compresi i popover del top layer aperti dopo di lui**: si vedono sopra ma non ricevono focus né clic e spariscono per gli screen reader. Un popover che deve funzionare con un modale aperto va messo dentro il `<dialog>` (vedi l'outlet dei toast).
- Un `$effect` che fa `push`/`unshift`/`splice` su un array `$state` lo legge anche (`length`): senza `untrack` l'effetto si riattiva da solo all'infinito (`effect_update_depth_exceeded`, la pagina si blocca e Playwright va in timeout sulla navigazione).
- Il contenuto passato in uno snippet a un elemento con `white-space: pre-wrap` (la descrizione di AlertBanner) conserva gli spazi e gli a capo del template: scrivere lo snippet senza spazi tra i blocchi, o rimettere `white-space: normal` sui propri elementi.
- Committare file nuovi su un branch e poi fare `git switch master` li toglie dalla cartella di lavoro (su `master` non esistono). Per annullare un commit tenendo tutto in staging: `git reset --soft <commit di prima>`, poi cambiare branch.
- PDF da un HTML locale: script Node con `chromium.launch({ executablePath: '~/.cache/ms-playwright/chromium_headless_shell-1243/chrome-headless-shell-linux64/chrome-headless-shell' })` dal `playwright` della root, `page.emulateMedia({ colorScheme: 'light', media: 'print' })`, `page.pdf({ format: 'A4', printBackground: true, preferCSSPageSize: true })`; nel CSS `@page { size: A4; margin: 15mm }` e `break-inside: avoid` sulle sezioni, altrimenti i titoli restano a fondo pagina staccati dalle tabelle. Il Read di Claude legge i PDF e ne mostra le pagine, per controllarli.
- `render()` di `vitest-browser-svelte`: `rerender(props)` riporta al valore del genitore ogni prop `$bindable` che il componente si era impostato da solo (`open`, `values`, `searchText`); un oggetto con getter/setter su variabili normali non è reattivo dentro il componente. Per seguire un valore che cambia: file `*.svelte.test.ts` con `$state`, o un componente di prova in `tests/fixtures/<nome>/`.
- Nei test con finestre di tempo (es. Tooltip che si apre subito entro 300 ms da una chiusura) sotto carico il tempo reale sfora: congelare `Date` con `vi.useFakeTimers({ toFake: ['Date'] })` lasciando veri i `setTimeout`.
- In Firefox, dopo un invio fallito, il fumetto di validazione nativo copre il campo sotto e si mangia i clic (anche in HTML puro): nei test scegliere con la tastiera. `toBeDisabled()` non riconosce `<fieldset role="radiogroup" disabled>`: controllare la proprietà `disabled`.
- Vite inlinea come data URI anche nei test le bandiere piccole di `flag-icons`: il test di FlagIcon accetta sia l'URL del file sia l'SVG inline.
- `<selectedcontent>` in Chromium: se il contenuto ricco dell'opzione scelta compare nello stesso giro in cui il browser riempie `selectedcontent`, l'observer di Svelte salta l'aggiornamento. Select rifà la selezione (`selectedIndex = -1` e poi quello di prima) quando compare `itemSnippet`.
- Vitest 5 non si installa con Node 25 (`engine-strict` nel `.npmrc` di aurora): si resta su Vitest 4.1 finché la macchina usa Node 25.
- Prefisso `--global-*` condiviso con la v4: **mai** riusare i nomi esatti della v4, che contengono triplette RGB (`--global-color-{background|contrast|grey|primary|secondary|error|warning|success}-{50..950}`, `--global-color-light-*`, `--global-color-dark-*`). Un'app che ha ancora override v4 nel CSS li applicherebbe ai token nuovi e romperebbe i colori in silenzio. I token semantici nuovi non hanno il gradino numerico (es. `--global-color-primary`, `--global-color-primary-soft`).
